Engenharia de Requisitos e Matriz de Rastreabilidade¶

Rastreabilidade bidirecional entre os Requisitos do Sistema (Funcionais e Não Funcionais), priorização MoSCoW, histórico formal de versionamento, Perguntas Norteadoras da Pesquisa (GQ01 a GQ13) e Decisões de Arquitetura (ADRs).

2. Metodologia de Levantamento e Priorização (MoSCoW)¶

A engenharia de requisitos do Trokim segue duas frentes fundamentais:

  1. Rastreabilidade com Guiding Questions (GQ01 a GQ13): Todo requisito deriva de uma necessidade diagnosticada na pesquisa com fontes oficiais (BCB, CVM, CFPB, ANPD). Requisitos sem origem em GQ são sumariamente rejeitados para evitar scope creep.
  2. Priorização MoSCoW:
  3. Must have: Mandatórios para o fluxo de valor do MVP e integridade do assistente (importação OFX/PDF, cálculos determinísticos com zero alucinação, RAG oficial com abstenção ativa, banco vetorial local e privacidade LGPD).
  4. Should have: Funcionalidades essenciais para a experiência de uso (comparação de cenários de orçamento, categorização assistida e baixa latência de recuperação).
  5. Could have: Funcionalidades de alto valor agregado previstas para as semanas 4 e 5 (assistente multimodal com visão em comprovantes e orquestração multiagentes; na Semana 4, a orquestração multiagente passou a Must have, nos RF18 a RF20).
  6. Won't have (nesta release): Conexões bancárias em nuvem via Open Finance ou agregação de credenciais bancárias (descartadas pela ADR 0005).

3. Requisitos Funcionais (RF)¶

ID Requisito Funcional Descrição Detalhada Priorização Origem ADR Relacionada Status de Implementação
RF01 Importação de extratos OFX O sistema deve ler e extrair transações financeiras de extratos bancários em formato .ofx, com perfil por banco (Nubank: conta e cartão, pessoal e Empresas; Banco do Brasil: conta corrente), natureza do lançamento e remoção de dados pessoais da contraparte. Must have GQ02, GQ03 ADR 0005 Implementado
RF02 Importação de faturas PDF O sistema deve extrair texto, datas e valores de faturas de cartão de crédito em formato .pdf, com acentos, milhar, sinal, parcelas e ano corretos, e perfil próprio para a fatura Ourocard do Banco do Brasil (conferida com o total da fatura). Must have GQ02, GQ03 ADR 0005 Implementado
RF03 Cálculo determinístico de totais O sistema deve calcular saldos, receitas, despesas e percentual de poupança exclusivamente por código matemático em Python, sem intervenção aritmética de LLMs. Must have GQ04, GQ07 ADR 0004 Implementado
RF04 Deduplicação de transações O sistema deve identificar e sinalizar automaticamente transações repetidas entre extratos bancários e faturas de cartão. Must have GQ02, GQ07 ADR 0004 Implementado
RF05 Consulta pedagógica via RAG O usuário pode enviar perguntas em linguagem natural respondidas com base nas publicações oficiais do BCB, CVM e CFPB. Must have GQ01, GQ05, GQ10 ADR 0003, ADR 0006, ADR 0007 Implementado
RF06 Abstenção ativa de IA O sistema deve recusar responder formalmente quando uma pergunta do usuário estiver fora do escopo ou não tiver respaldo oficial comprovado. Must have GQ05, GQ10 ADR 0003, ADR 0006 Implementado
RF07 Dashboard consolidado no Android O aplicativo móvel deve exibir o resumo financeiro, saldo líquido, métricas de poupança e distribuição por categoria. Must have GQ01, GQ07, GQ13 ADR 0001, ADR 0015 Implementado
RF08 Simulação e comparação de cenários O sistema deve permitir comparar dois cenários orçamentários (ex.: Cenário Padrão vs. Otimizado com meta de reserva de emergência). Should have GQ06, GQ08, GQ12 ADR 0004 Previsto (Semana 4)
RF09 Categorização automática assistida O sistema deve inferir a categoria das transações por regras locais e permitir conferência e ajuste no app; a correção vira regra do estabelecimento, aplicada aos lançamentos já importados e aos próximos arquivos. Should have GQ07, GQ11 ADR 0004, ADR 0017, ADR 0018, ADR 0020 Implementado
RF10 Auditoria e citação direta de fontes Cada orientação gerada pelo assistente deve referenciar explicitamente o órgão oficial (ex.: Banco Central) e a seção documental correspondente. Must have GQ05, GQ08 ADR 0003, ADR 0006, ADR 0007 Implementado
RF11 Busca híbrida de evidências O motor de recuperação deve combinar vetores densos (FastEmbed) com similaridade esparsa (TF-IDF palavras + n-grams de caracteres) com ponderação calibrada. Must have GQ05, GQ10 ADR 0007 Implementado
RF12 Ingestão e persistência vetorial local O sistema deve armazenar embeddings e metadados na tabela virtual vec0 do SQLite-Vec, reingerindo automaticamente em caso de alteração no corpus via hash SHA-256. Must have GQ03, GQ10 ADR 0002, ADR 0007, ADR 0019 Implementado
RF13 Interface conversacional com cartões de fontes O app mobile e a API devem disponibilizar canal de diálogo com renderização de cartões destacando a instituição, trecho, score e link do documento governamental. Must have GQ01, GQ05 ADR 0001, ADR 0003 Implementado
RF14 Gerador sintético de extratos e faturas O projeto deve conter geradores automatizados de dados financeiros fictícios em formatos OFX e PDF para validação contínua em conformidade com a LGPD. Must have GQ02, GQ03 ADR 0005, ADR 0006 Implementado
RF15 Ajustes do aplicativo O app deve permitir escolher o tema (sistema, claro ou escuro), reduzir animações, desligar a abertura animada, editar o endereço da API local e testar a conexão, salvando as preferências apenas no aparelho. Should have GQ01, GQ03 ADR 0013 Implementado
RF16 Histórico de conversas com título automático O assistente guarda localmente o histórico de conversas e usa o LLM local para dar a cada uma um título curto (3 a 6 palavras), com título determinístico de reserva e título provisório enquanto o modelo trabalha, sem enviar dados a terceiros. Should have GQ01, GQ03, GQ05 ADR 0014 Implementado
RF17 Síntese generativa fundamentada A API e o app devem redigir respostas em linguagem natural com o modelo configurado (LiteLLM/Ollama), ancoradas nas evidências oficiais, com citação por fonte, abstenção ativa fora de escopo ou sem evidência e erro claro (503) se o modelo estiver indisponível. Must have GQ04, GQ05, GQ10, GQ11 ADR 0009, ADR 0008 Implementado
RF18 Orquestração multiagente com trilha O sistema deve responder por quatro agentes (Research, Analysis, Communication e Validation) coordenados por um orquestrador determinístico e devolver, com a resposta, a trilha de cada passo (agente, estado, resumo e duração). Só o Communication usa LLM. Must have GQ05, GQ10 ADR 0016 Implementado
RF19 Validação determinística antes de responder Nenhuma resposta multiagente pode sair sem a checagem do Validation Agent (números sem suporte, citações inválidas, conselhos fora de escopo e abstenção inconsistente). Com bloqueio persistente, a resposta é rejeitada de forma segura, sem inventar conteúdo. Must have GQ05, GQ11 ADR 0016, ADR 0004 Implementado
RF20 Análise determinística de perguntas numéricas Todo cálculo de uma pergunta (resumo, categorias, meta e cenários) é feito por código pelo Analysis Agent e entregue ao Communication como resultado pronto. Sem dados suficientes, o sistema diz o que falta em vez de estimar. Must have GQ07, GQ08, GQ09 ADR 0016, ADR 0004 Implementado
RF21 Trilha dos agentes no app O app deve mostrar, por resposta, "como cheguei a essa resposta": os passos dos agentes, os cálculos, as evidências e, em abstenção ou rejeição, o motivo em linguagem simples. O modo multiagente é opcional em Ajustes. Should have GQ01, GQ10 ADR 0016 Implementado
RF22 Contas e situação do período Cada arquivo pertence a uma conta com dono (pessoal ou empresa) perguntado uma vez; o sistema detecta fatura aberta ou fechada e extrato parcial, permite confirmar e ajustar o período, substitui os lançamentos ao reimportar o mesmo período, aponta lacunas e avisa de arquivo no lugar errado antes de importar. Must have GQ02, GQ03, GQ13 ADR 0018 Implementado
RF23 Controle de parcelamentos O sistema agrupa a mesma compra parcelada entre faturas e mostra parcela atual, quanto falta e a projeção mensal do que já está comprometido. Should have GQ07, GQ09 ADR 0018 Implementado
RF24 Transferências entre contas próprias O dinheiro que só mudou de conta (inclusive o Pix que paga a fatura de outro banco) sai dos totais: ligação certa pela conta de destino, sugestões por valor e data para o usuário confirmar ou recusar, e desfazer. Must have GQ07, GQ13 ADR 0018 Implementado
RF25 Visões de caixa e competência por dono O Resumo alterna entre gastos (competência) e caixa, filtra por dono (Tudo, Pessoal, Empresas) e mostra o total por conta, com os números calculados só no backend. Should have GQ07, GQ13 ADR 0018, ADR 0004 Implementado
RF26 Receber arquivo por "Compartilhar" No Android, o app aceita OFX e PDF enviados por "Compartilhar" ou "Abrir com" e abre o fluxo de importação já com o arquivo, sem enviá-lo a terceiros. Should have GQ01, GQ03 ADR 0018 Implementado
RF27 Leitura assistida de documentos O app deve permitir fotografar ou selecionar comprovantes e faturas digitalizadas e apresentar uma prévia antes da leitura. Must have GQ01, GQ02, GQ03 ADR 0021 Backend HTTP implementado (#96); mobile com mock até a #97
RF28 Revisão humana antes da importação Os campos extraídos devem ser editáveis, indicar confiança e bloqueios, e só podem ser confirmados por ação explícita; documentos ilegíveis devem pedir nova captura. Must have GQ01, GQ02, GQ03 ADR 0021 Backend HTTP implementado (#96); mobile com mock até a #97
RF29 Bancos suportados, níveis de suporte e tutoriais O app lista os bancos suportados com selo Validado ou Experimental, tutorial de exportação por banco e aviso de que banco experimental ainda não foi conferido com arquivo real. A API expõe a lista em GET /v1/banks e reconhece o banco pelo conteúdo do arquivo (OFX, PDF ou CSV). Banco novo é um registro e um perfil, sem alterar os demais. Should have GQ01, GQ03 ADR 0022, ADR 0017 Implementado; PicPay, Mercado Pago, Inter, C6 e Itaú seguem experimentais (sem arquivo real).
RF31 Persistência local da biblioteca Lançamentos, contas, arquivos, transferências confirmadas e regras de categoria sobrevivem ao reinício da API e do app. A fonte da verdade é o aparelho, que guarda o retrato cifrado (AES-256-GCM, chave no armazenamento seguro do sistema); a API o recebe ao abrir o app e o mantém só em memória. O SQLite local da API, atrás de uma porta de repositório, segue como opção para quem usa a API sem o app. Só mudam quando o usuário altera algo. Must have GQ03, GQ06 ADR 0024, 0025 Implementado
RF32 Backup criptografado e restauração O usuário exporta a biblioteca em um arquivo .trokim protegido por senha (AES-256-GCM, chave por scrypt) e a restaura em outro aparelho, substituindo ou mesclando sem duplicar. A senha nunca é gravada. Should have GQ03, GQ06 ADR 0024 Implementado

4. Requisitos Não Funcionais (RNF)¶

ID Requisito Não Funcional Descrição Detalhada Priorização Origem ADR Relacionada Status de Implementação
RNF01 Privacidade Local-First (LGPD) Os extratos bancários e transações devem ser armazenados localmente no dispositivo em SQLite, sem persistência ou transmissão para servidores de terceiros. Must have GQ03, GQ06 ADR 0002, ADR 0005 Validado
RNF02 Explicabilidade e acurácia aritmética O motor de cálculo determinístico deve possuir 100% de acurácia numérica e cobertura por testes automatizados com pytest (0% de erro ou alucinação). Must have GQ04, GQ11 ADR 0004 Validado
RNF03 Portabilidade e performance mobile A interface do app Android deve manter taxa de quadros estável e baixo consumo de memória através da compilação nativa em Flutter. Must have GQ01 ADR 0001 Validado
RNF04 Baixa latência de recuperação As consultas RAG locais devem recuperar as evidências no banco vetorial e responder em menos de 100 ms em desenvolvimento local (alcançado ~12,4 ms). Should have GQ05, GQ10 ADR 0003, ADR 0007 Superado
RNF05 Arquitetura limpa em camadas O backend deve isolar estritamente o domínio das rotas e adaptadores (routers → services → domain), prevenindo acoplamento indevido. Must have GQ03 ADR 0002 Validado
RNF06 Testabilidade com dados sintéticos Toda a suíte de testes e validação de hipóteses deve rodar com dados sintéticos em research/synthetic_data/, sem uso de dados reais de usuários. Must have GQ02, GQ03 ADR 0005, ADR 0006 Validado
RNF07 Desacoplamento via Ports & Adapters O pipeline de embeddings e vector store deve adotar interfaces puras (EmbeddingModel, VectorStore) permitindo substituição de provedores sem alterar o domínio. Must have GQ03, GQ10 ADR 0002, ADR 0007 Validado
RNF08 Auditabilidade e determinismo no benchmark O protocolo de avaliação deve ser estritamente reproduzível com saída JSON padronizada, controle de código de saída (exit code) e hashes de integridade. Must have GQ05, GQ08 ADR 0006 Validado
RNF09 Metas empíricas do RAG O sistema de recuperação deve atingir métricas mínimas auditadas no benchmark: Recall@3 ≥ 90%, resposta fundamentada ≥ 90% e abstenção ética = 100%. Must have GQ05, GQ08 ADR 0006, ADR 0007 Superado
RNF10 Acessibilidade e conforto visual A interface deve seguir o tema claro/escuro do aparelho, respeitar "reduzir movimento", manter contraste legível, tipografia embarcada e rolagem sem deformação. Must have GQ01, GQ07 ADR 0011, ADR 0013, ADR 0021 Implementado
RNF11 Arte de marca com licença livre Toda arte da marca (logo, mascote, fontes) deve ter licença que permita uso comercial (CC0, domínio público, OFL ou paga), com origem registrada e arquivos trocáveis sem alterar código. Should have GQ01, GQ03 ADR 0012 Implementado
RNF12 Motores de visão intercambiáveis e consentimento OCR e modelo de visão ficam atrás de portas e se trocam só por configuração. O OCR é local por padrão; o modelo de visão vem desligado, e um provedor remoto (que leva a imagem para fora do aparelho) só é usado com consentimento explícito. Imagem, texto lido e resposta do modelo nunca são registrados em log. Must have GQ02, GQ03 ADR 0021 Implementado
